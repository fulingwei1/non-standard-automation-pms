# 非标自动化项目管理系统真正用起来路线图

## 目标

适用对象：一两百人的非标自动化设备公司。

判断标准不是页面多，而是销售、售前、项目、采购、生产、交付、财务每天能沿着同一条主线做事：

1. 销售录入商机和客户需求。
2. 售前技术支持接单、澄清需求、出方案、估成本、配合投标。
3. 赢单后生成项目交接包，项目经理接收范围、成本、风险、计划。
4. 项目阶段推进时，采购、生产、装配、调试、验收按项目同一条线更新。
5. 毛利、交期、风险、变更、验收和复盘能回到同一个项目闭环。

## 当前问题判断

系统不是没有功能，而是功能太散：

| 业务段 | 当前现象 | 对真实使用的影响 |
|---|---|---|
| 权限和菜单 | 页面、路由、权限点存在重复和历史入口 | 用户不知道该从哪里进，同一岗位看到太多旧入口 |
| 销售到售前 | 商机、方案、成本、投标、工单分散 | 销售觉得流程断，售前任务接不住 |
| 售前技术支持 | 需求调研、方案、技术参数、工单、投标、知识库分散 | 售前工程师需要跳多个页面，资料难复用 |
| 项目管理 | 项目看板、PMO、甘特、资源、成本、评审、风险、ECN、收尾分散 | 项目经理缺一个日常工作台 |
| 项目后续模块 | 采购、生产、装配、交付、验收都能按项目查，但入口分散 | 公司管理层看不到“一台设备从签单到验收”的完整状态 |

## 主入口设计

不要把所有页面删掉重做。先确定主入口，其它页面保留为子能力或旧路由重定向。

| 主入口 | 面向岗位 | 应合并的能力 | 当前落点 |
|---|---|---|---|
| 销售工作台 | 销售、销售经理 | 客户、商机、报价、合同、售前申请、赢单交接 | 销售模块现有工作台继续收敛 |
| 售前技术支持中心 | 销售、售前工程师、售前主管 | 需求调研、方案、技术参数、成本估算、投标、工单、知识库、模板 | `/presales/technical-solutions` 已开始合并 |
| 项目管理中心 | 项目经理、PMO、工程负责人 | 项目看板、项目详情、WBS、任务、甘特、资源、里程碑、项目评审 | 当前分散在 `/board`、`/project/dashboard-center`、`/gantt-resource` 等 |
| 项目执行中心 | 机械、电气、软件、装配、调试 | 任务领取、进度填报、工时、问题、现场资源 | 当前分散在任务、工程师工作台、装配、生产执行 |
| 项目成本毛利中心 | 项目经理、财务、老板 | 预算、实际成本、工时成本、报价成本、毛利偏差、变更影响 | `/project/cost-center` 已有雏形 |
| 交付验收中心 | 项目经理、品质、交付、售后 | FAT、SAT、现场问题、验收单、整改闭环、售后交接 | 当前分散在生产验收、项目交付、售后 |

## 售前技术支持合并方案

近期目标：把售前从“页面集合”变成“接单到交付物”的工作台。

主入口：`/presales/technical-solutions`

建议页签：

| 页签 | 作用 | 来源页面 |
|---|---|---|
| 需求调研 | 客户需求澄清和现场调研 | `RequirementSurvey` |
| 技术方案 | 方案编制、版本、评审 | `PresaleProposals` |
| 技术参数 | 参数模板、行业分类、成本估算基础 | `TechnicalParameterManagement` |
| 成本估算 | 初版成本、毛利预警、报价输入 | `PresalesCostEstimation` |
| 投标支持 | 技术标、商务标协同、投标状态 | `BiddingCenter`、`PresaleBids` |
| 工单看板 | 销售发起支持、售前处理、经理派工 | `PresalesTasks`、`PresaleTicketBoard` |
| 知识模板 | 方案模板、案例、售前复用资产 | `PresaleTemplates` |

保留旧 URL，但逐步重定向到中心页签，避免老链接失效。

当前已落地：

- `/presales/technical-solutions` 已扩展为售前技术支持中心。
- `需求调研 / 技术方案 / 技术参数 / 成本估算 / 投标支持 / 知识模板 / 工单看板` 已能在中心内切换。
- `/requirement-survey`、`/presales/solutions`、`/presales/technical-parameters`、`/presales/cost-estimation`、`/bidding`、`/presales/bids`、`/presales/templates`、`/presale-templates`、`/presales-tasks`、`/presales/ticket-board` 已作为兼容入口跳到中心页签。
- `/sales/presales-tasks`、`/project-presales-tasks` 已作为兼容入口跳到 `tab=reviews`，并保留 `type/status/projectId` 等筛选条件。
- 全局 `/knowledge-base` 暂不并入售前中心，保留为公司级知识库。

下一批建议：

1. 销售工作台里的“发起售前支持”统一落到同一张售前工单，不再新造一套申请表。
2. 把售前中心的数据加载从多个散接口逐步迁到聚合上下文接口。

## 项目管理合并方案

项目管理的问题和售前类似：已经有很多子模块，但项目经理缺一个稳定日常入口。

建议新增或扩展主入口：`/project/management-center`

建议页签：

| 页签 | 作用 | 来源页面 |
|---|---|---|
| 项目看板 | 所有项目、卡片视图、流水线视图 | `ProjectBoard` |
| 项目驾驶舱 | PMO 总览、健康监控 | `ProjectDashboardCenter` |
| 任务计划 | WBS、任务、里程碑、进度报告 | `TaskCenter`、`WBSTemplateManagement`、`MilestoneManagement`、`ProgressReport` |
| 甘特资源 | 任务依赖、资源负载 | `GanttAndResource` |
| 技术评审 | PDR/DDR/PRR/FRR/ARR 评审 | `ProjectReviewList`、`ProjectReviewDetail` |
| 风险变更 | 风险、ECN、问题、影响分析 | `RiskManagement`、`ECNManagement`、`ECNCostImpact`、`ECNMaterialImpact` |
| 成本毛利 | 预算、工时、成本、毛利预测 | `ProjectCostCenter`、`MarginPrediction` |
| 交付收尾 | 交付计划、验收、结项、复盘、经验 | `ProjectClosing`、验收/交付相关页面 |

路由策略：

- `/projects`、`/board` 统一作为项目列表入口，后续可重定向到 `management-center?tab=board`。
- `/pmo/dashboard`、`/project/dashboard-center` 统一作为 `management-center?tab=dashboard`。
- `/gantt-resource` 保留为深链接，但菜单只露出项目管理中心。
- `/project-closing` 保留为深链接，但菜单归入项目管理中心的交付收尾页签。
- `/projects/:id/*` 继续保留项目详情深链接，不强行塞进全局页签。

## 售前到项目的交接包

这是系统能不能真正跑起来的核心。

赢单后必须生成一份项目交接包，至少包括：

| 交接内容 | 来源 | 进入项目后的用途 |
|---|---|---|
| 客户和合同信息 | 销售、合同 | 项目基础信息 |
| 需求调研结论 | 售前需求调研 | 项目范围、验收标准 |
| 技术方案版本 | 方案管理 | 设计输入、技术评审 |
| 技术参数模板 | 技术参数 | BOM、测试规格、标准工时 |
| 成本估算和毛利底线 | 售前成本 | 项目预算、毛利预警 |
| 风险和假设 | 售前/投标 | 项目风险清单 |
| 交期和关键里程碑 | 销售/售前 | 项目计划初稿 |
| 未闭环事项 | 售前工单/评审 | 项目待办和阶段门 |

交接动作要做成系统按钮：`赢单交接 -> 生成项目 -> 生成WBS/里程碑初稿 -> 生成项目待办`。

## 分阶段落地

### Phase 1：入口收敛

目标：用户先知道从哪里进。

- 销售：商机、报价、合同、售前申请只保留一个主入口。
- 售前：`/presales/technical-solutions` 作为售前技术支持中心。
- 项目：建立 `/project/management-center` 或扩展现有项目中心。
- 菜单只放主入口，旧入口只做跳转和深链接。

### Phase 2：流程闭环

目标：销售到售前到项目能走通。

- 商机创建售前工单。
- 售前工单关联需求调研、方案、成本、投标。
- 赢单后生成项目交接包。
- 项目创建后自动带出范围、成本、风险、里程碑初稿。

### Phase 3：项目后续模块收口

目标：项目经理每天只看一个项目中心。

- 项目中心补齐任务计划、技术评审、风险变更、成本毛利、交付收尾。
- 采购、生产、装配、验收页面保留专业视图，但必须能从项目详情进入。
- 每个后续模块都要回写项目状态、风险、成本或验收结果。

### Phase 4：权限和角色验收

目标：100-200 人公司能按岗位使用。

最少角色：

| 角色 | 主入口 |
|---|---|
| 销售 | 销售工作台、售前申请、报价合同 |
| 售前工程师 | 售前技术支持中心 |
| 售前主管 | 售前派工、评审、负荷 |
| 项目经理 | 项目管理中心 |
| 工程师 | 我的任务、技术评审、工时 |
| 采购/仓库 | 采购执行、齐套、收发料 |
| 生产/装配 | 生产执行、装配任务、异常 |
| 品质/交付 | 验收、整改、交付计划 |
| 财务/老板 | 成本毛利、项目健康、经营看板 |

权限原则：

- 菜单权限按主入口配置。
- 操作权限按按钮/API 配置。
- 旧页面不单独暴露菜单权限，避免同一个岗位看到多套入口。

## 最近三步执行建议

1. 统一销售工作台里的“发起售前支持”动作，确保商机、方案评审、技术支持都落到同一张售前工单。
2. 新建或扩展项目管理中心，把项目看板、PMO、任务计划、甘特资源、技术评审、风险变更、成本毛利、交付收尾放到同一入口。
3. 做一条端到端验收脚本：商机 -> 售前工单 -> 方案/成本 -> 赢单交接 -> 项目 -> 任务/评审 -> 验收/收尾。

这三步完成后，系统才会从“很多功能模块”变成“公司能按流程每天用的系统”。

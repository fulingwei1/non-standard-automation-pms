# 非标自动化项目管理系统全流程合并与可用化方案

## 结论

系统不要再按“销售模块、售前模块、项目模块”各自做大而全页面。对一两百人的非标自动化公司，真正可用的形态应该是：

1. 销售只负责机会推进、报价、合同和发起售前/立项。
2. 售前技术支持合并到统一售前中心，承接需求澄清、方案、成本、技术参数、投标、评审和售前任务。
3. 合同签署后必须走 PMO 立项，立项审批通过后生成项目。
4. 项目工作台成为后段唯一承接页，统一展示销售/售前交接包和工程、供应链、生产、质检、交付、验收状态。
5. 后段模块继续保留专业页面，但必须从项目工作台带 `project_id` 进入，不能再孤立创建和孤立查看。

这条主线比“到处再做一个看板”更重要。用户打开系统时要能回答三个问题：现在该谁处理、缺什么资料、下一步去哪处理。

## 目标架构

### 1. 统一入口

| 业务域 | 主入口 | 处理原则 |
| --- | --- | --- |
| 销售 | `/sales/workstation`, 销售线索/商机/报价/合同页面 | 保留销售动作，不再内嵌散落的售前技术页面 |
| 售前技术支持 | `/presales/technical-solutions`, `/presales/workbench` | 合并工单、任务、方案、成本、技术参数、投标、评审 |
| PMO 立项 | `/pmo/initiations` | 合同签署后发起立项，不允许合同直接无审查生成执行项目 |
| 项目执行 | `/projects/:id/workspace` | 后段统一承接页，显示交接包、状态和下一步动作 |
| 后段专业模块 | 采购、生产、质量、交付、验收、财务等原专业页 | 保留专业能力，但必须从项目工作台带上下文进入 |

### 2. 统一上下文

全链路必须统一传递以下字段：

```text
lead_id -> opportunity_id -> quote_id -> contract_id -> initiation_id -> project_id
presale_ticket_id -> presale_solution_id -> baseline_cost
pm_involvement_required -> pm_involvement_risk_level -> pm_assigned
```

项目工作台的 `handover_context` 是上游唯一交接包，`downstream_context` 是后段唯一状态汇总。后续模块不能各自再拼一套销售/售前查询逻辑。

### 3. 旧入口处理

旧入口不要马上删除。先统一重定向，并保留查询参数：

- `/sales/presales-tasks` -> `/presales/technical-solutions?tab=reviews`
- `/project-presales-tasks` -> `/presales/technical-solutions?tab=reviews`
- `/presales-tasks` -> `/presales/technical-solutions?tab=reviews`
- `/presales/cost-estimation` -> `/presales/technical-solutions?tab=cost`
- `/presales/solutions` -> `/presales/technical-solutions?tab=solutions`
- `/presales/technical-parameters` -> `/presales/technical-solutions?tab=parameters`

删除旧页面必须等到测试和菜单都切干净。

## 分阶段落地

### Phase 1：入口止血

目标：用户不再被重复菜单和重复页面绕晕。

任务：

1. 售前相关旧路由全部重定向到统一售前中心。
2. 菜单只暴露一个售前技术支持中心，销售和项目侧只保留快捷入口。
3. 对每个旧入口补路由测试，确认参数不丢。
4. 暂不删除旧组件，先避免误删。

验收：

- 销售、售前工程师、PM 从不同入口进入的是同一套售前数据。
- 搜索、状态、商机、项目筛选参数都能保留。

### Phase 2：售前中心合并

目标：售前技术支持从“散的页面”变成一个工作中心。

统一中心应包含这些 Tab：

| Tab | 内容 |
| --- | --- |
| 评审/工单 | 售前支持申请、方案评审、PM 介入风险 |
| 任务 | 统一售前任务中心，支持接单、进度、交付物 |
| 方案 | 售前方案库和项目方案 |
| 成本 | 成本估算、报价成本基线 |
| 技术参数 | 参数模板、匹配、成本估算 |
| 投标 | 招投标资料和技术评审 |
| 知识 | 模板、案例、踩坑记录 |

验收：

- 新建售前工单后，在看板、任务中心、项目交接包中能看到同一条记录。
- PM 提前介入状态在售前看板、售前任务中心、项目工作台都能看到。
- 售前交付物能进入项目交接包。

### Phase 3：项目工作台成为后段承接页

目标：项目经理一打开项目就知道上游交接是否齐套、后段哪里有问题。

项目工作台必须展示：

- 合同、商机、报价、售前方案、售前工单。
- 成本基准：报价成本、售前估算、项目预算。
- PM 提前介入：风险等级、风险因素、PM 是否分配。
- 工程：技术评审、ECN。
- 供应链：BOM、齐套率、关键缺料。
- 生产：生产计划、工单进度。
- 质量：质检不合格和不良数量。
- 交付：排产、任务冲突。
- 验收：验收单、通过率。
- 后续动作：按优先级列出该谁处理。

下一步重点：

1. `next_actions` 增加深链接，点击能带 `project_id` 打开对应专业模块。
2. PMO 立项详情在审批前也展示售前交接包，避免审批时看不到风险。
3. 项目工作台增加“缺资料补齐入口”，缺合同、缺方案、缺成本时直接跳到对应动作。

### Phase 4：后段模块只做专业执行

目标：采购、生产、质量、交付、验收不再各自形成孤岛。

| 模块 | 合并方式 |
| --- | --- |
| 工程评审/ECN/BOM | 保留专业页面，从项目工作台进入时带 `project_id`，结果回流 `downstream_context` |
| 采购申请/采购订单/到货 | 保留采购执行中心，创建时默认项目、设备、BOM 上下文 |
| 外协/物料/齐套 | 以项目齐套为主指标，旧齐套算法保留为服务层能力 |
| 生产计划/工单 | 从项目进入时默认项目排产，进度回写项目工作台 |
| 质量/验收 | 不合格、验收失败必须形成项目后续动作 |
| 财务/付款/成本 | 合同付款计划、预算执行、实际成本都回到项目成本视图 |

验收：

- 所有后段创建表单从项目进入时不用重复选项目。
- 专业页面处理后，项目工作台刷新能看到状态变化。
- 不允许只在专业页成功、项目页仍显示空状态。

### Phase 5：权限和菜单收口

目标：一两百人的公司能按岗位直接用，不需要管理员手工猜权限。

角色建议：

| 角色 | 默认入口 |
| --- | --- |
| 销售 | 销售工作台、客户、线索、商机、报价、合同、发起售前 |
| 售前工程师 | 售前工作台、售前任务、方案、参数、成本、投标 |
| PM/项目经理 | PMO 立项、项目工作台、项目任务、风险、会议、问题 |
| 采购 | 采购执行、物料、供应商、到货、齐套 |
| 生产 | 生产计划、工单、装配任务 |
| 质量 | 质检、验收问题、不合格处理 |
| 财务 | 合同付款、项目成本、结算 |
| 管理层 | 统一经营/项目/风险看板 |

权限不要先重写全系统。先把 P0 链路角色跑通，再清理功能模块管理和菜单注册。

## P0 验收用例

必须用端到端用例证明“真能用”：

1. 线索转商机。
2. 商机发起售前技术支持。
3. 售前完成方案、成本、技术参数、交付物。
4. 高风险商机触发 PM 提前介入。
5. 报价审批通过并生成合同。
6. 合同签署后发起 PMO 立项。
7. PMO 审批生成项目，并回写合同、售前方案、售前工单。
8. 项目工作台显示完整交接包和 PM 风险。
9. 从项目工作台发起采购申请、交付排产、物料预留。
10. 采购/生产/质量/验收处理结果回流项目工作台。

## 不建议做的事

- 不要先大规模重写 UI。
- 不要先删除旧模块。
- 不要再新增一个“总览大屏”来掩盖流程断点。
- 不要让后段模块继续各自查询销售/售前数据。
- 不要只用 import 成功或构建成功作为交付标准，必须有端到端链路测试。

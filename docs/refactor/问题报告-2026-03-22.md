# 非标自动化 PMS 问题报告（2026-03-22）

## 1. 执行摘要

当前系统核心问题不是“功能少”，而是“**假可用**”与“**错误被吞**”。

初始状态下，未实现接口可被 stub 伪装为成功返回，关键模块加载失败后系统仍继续启动，导致前端误判服务正常、排障成本高、线上风险隐蔽。

本次已完成 Phase 0 的主体止血改造（1~7批），核心方向：
- 禁止假成功（stub 默认 501 + 默认禁用）
- 关键域 fail-fast（默认严格模式）
- 增加路由加载失败汇总
- 增加 CI 防回退守卫（防止把 stub 默认值改回危险状态）

---

## 3. 问题分级

## P0（立即影响稳定性）
1. **Stub 假成功**：未实现接口返回 200，掩盖后端缺失。
2. **吞错启动**：模块加载失败仅打印，不中断启动。
3. **空路由兜底**：`create_api_router()` 失败后仍用空路由继续运行。
4. **关键链路硬故障**：ITR 导入错误、2FA 依赖缺失。

## P1（高维护成本）
1. `api.py` 职责过载，跨域耦合严重。
2. 前端“API+mock/fallback混用”比例高，真实错误不可见。

## P2（技术债）
1. 高置信死代码：
   - `app/api/v1/endpoints/template_configs/apply.py`
   - `app/api/v1/endpoints/template_configs/crud.py`
   - `app/api/v1/endpoints/base_crud_router.py`
2. 可删除依赖（前端 0 引用）：
   - `@dnd-kit/utilities`
   - `@radix-ui/react-popover`
   - `@radix-ui/react-scroll-area`
   - `@radix-ui/react-separator`
   - `@radix-ui/react-tabs`
   - `zustand`

---

## 4. 已完成整改（Phase 0，1~7批）

1. `stub_endpoints` 默认改为 `501 Not Implemented`。
2. 默认禁用 stub：`ENABLE_STUB_ENDPOINTS=false`。
3. 新增兼容开关：`ALLOW_STUB_SUCCESS=true` 才允许返回 200。
4. 移除 `api.py` 的空路由 fallback。
5. 引入严格模式：`STRICT_API_ROUTER=true`（默认）。
6. 大范围关键业务域改为 fail-fast（已覆盖核心主链路与多数业务域）。
7. 修复 ITR 导入：改为从 `app.models` 聚合导入。
8. 2FA 链路容错：qrcode 缺失时返回明确 `503`，不再隐式拖垮。
9. 增加“路由加载失败汇总”输出（启动末尾统一打印失败项）。
10. 增加 CI 防回退守卫：
    - `scripts/ci_guard_stub_defaults.py`
    - `.github/workflows/guard-stub-defaults.yml`

---

## 5. 未完成项（收尾）

1. 在 `STRICT_API_ROUTER=true` 下执行一次**全量启动回归**。
2. 根据回归结果形成最终分层：
   - 关键域（必须 fail-fast）
   - 可降级域（允许 warning）
3. 补充前后端 API 对账 CI（path + method）。
4. 推进前端 30 个“部分集成页面”去 mock/fallback。

---

## 6. 风险评估（当前）

- **高风险已显著下降**：假成功与吞错启动路径已被主动作废。
- **剩余风险**：严格模式下若某些低优先域依赖不完整，可能导致启动失败；需通过一次全量回归收敛。

---

## 7. 建议验收标准

1. 启动日志中“路由加载失败汇总”可读、可追踪。
2. 生产环境 stub 命中为 0。
3. 关键域加载失败时，服务必须启动失败。
4. 核心链路 e2e（登录→项目→采购→审批）全通过。
5. CI 阻止不安全默认值回退。

# 发货链路端到端验收报告

**链路**：项目/销售订单 → 发货单 → 审批 → 实际发货 → 签收
**验收方式**：真实角色登录 → 逐环节调真实 API → 每步核对数据库 → 正向 + 反向 → 整库还原清理
**日期**：2026-07-02
**环境**：后端 `app.main:app`@127.0.0.1:8002；DB SQLite `data/app.db`（验收前整库备份，验收后已还原，零残留）
**结果**：链路主干 **端到端跑通**；检查项 **8/9 通过**，唯一未通过为**已确认的高危缺陷**（发货链路无 RBAC）。

---

## 1. 测试账号与角色

| 用户 | 角色 | 用途 |
|---|---|---|
| acc_sales_mgr | 验收-销售经理(充当商务/发货) | 建发货单、审批、发货、签收 |
| acc_worker | 验收-车间工人 | 无关角色越权对照 |

> 前置：发货单必须关联**带 `project_id` 的销售订单**（现有 60 条销售订单均未设 project_id），验收为此创建了带项目的测试销售订单。

---

## 2. 正向主链路（单据流转与三方核对）

代表性一次完整执行（单据号，均已在验收后还原清理）：

| # | 环节 | 操作角色 | 单据 | 状态流转 | 三方核对 |
|---|---|---|---|---|---|
| 1 | 建发货单 | 商务 | 发货单（id 4） | approval=pending / delivery=draft | ✅ 带 order_id=61、project_id=104 |
| 2 | 审批 | 商务 | — | approval **approved** / delivery approved | ✅ DB approval_status=approved |
| 3 | 实际发货 | 商务 | — | delivery→**shipped**，记 ship_date | ✅ DB delivery_status=shipped |
| 4 | 签收 | 商务 | — | delivery→**received**，记 receive_date | ✅ DB delivery_status=received |

**状态机验证**：发货单从 草稿/待审 → 审批通过 → 已发货 → 已签收，各步 DB 状态与时间戳正确。

---

## 3. 越权 / 反向验收

| 用例 | 期望 | 结果 |
|---|---|---|
| N1 未审批直接发货 | 拒绝 | ✅ 400（"发货单未审批通过，不能发货"） |
| N2 未发货直接签收 | 拒绝 | ✅ 400（"仅已发货的发货单可以确认签收"） |
| N3 无关角色(工人)审批发货单 | 应 403 | ❌ **200 未拦截**（见发现 SH1） |
| N4 未携带 token 访问 | 401 | ✅ 401 |

**状态机控制完善**：发货/签收严格按 审批→发货→签收 顺序，越序操作被 400 拒绝。

---

## 4. 发现问题（FINDINGS）

| 编号 | 严重度 | 环节 | 问题 | 影响 |
|---|---|---|---|---|
| **SH1** | 高 | 发货单鉴权 | `business_support_orders/delivery_orders` 所有端点仅 `deps.get_current_user`，**无细粒度 RBAC**；无关角色(车间工人)可审批发货单、可发货/签收 | 发货审批缺职责分离与越权防护（与生产链路 PR2 同类问题） |

> 附带观察：发货单创建强依赖"销售订单必须已关联项目"，但销售订单默认不带 project_id，需先在项目交付页/销售订单侧回填 project_id，否则发货无法发起。

---

## 5. 数据清理

- 本链路创建的测试数据（测试销售订单、发货单）与测试用户/角色，验收后从**验收前整库备份还原**。
- 还原后核对：`sales_orders=60 / delivery_orders=3 / users=195` 与基线一致，测试标记数据 **0 残留**，`PRAGMA foreign_key_check` 回到基线（69）。

---

## 6. 结论

发货链路**业务主干端到端跑通**：发货单从创建、审批、实际发货到签收全流程状态流转正确，状态机对越序操作（未审批发货、未发货签收）有效拦截。

**待修复**：SH1 发货单端点缺 RBAC（高，建议补发货/审批权限，与销售/采购口径一致）。
